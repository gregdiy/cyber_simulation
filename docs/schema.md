# Enterprise Security Log Dataset — Schema Documentation

**Dec 2025 – Jan 2026 | Multi-User Pivot Living-Off-The-Land Campaign | ATK_50673**

---

## Overview

This dataset contains **realistic enterprise security logs** with an embedded **multi-stage attack campaign** that pivots across identities and privilege levels.

Logs include:

- **Windows security events** (process execution, authentication, network connections, file operations, system activity)
- **Defense / observability logs** (EDR, DLP, SIEM, PAM, MFA-style alerts/blocks/denials)
- **Service account background activity** (continuous automation noise at enterprise scale)
- **Event-level ground truth** for attacker actions (`attack_id`)

**Generation model:** both benign and attack activity are generated by an AI-driven simulation framework. The attacker is guided by a **100+ parameter defensive environment** (controls, coverage, enforcement, alert overlap/noise) and optimizes its behavior under that posture.

### Key characteristics (this release)

| Metric | Value |
|---|---|
| Total logs | 7,961,002 |
| Duration | 25 days |
| Attacker actions (`attack_id` non-null) | 345 |
| Defense / observability logs | 142,454 |
| Attack-triggered observability events | 285 |

> **Note on observability count:** not de-duplicated — a single attacker action can generate multiple observability events across different tools or alert types.

## Log Type Categories

All logs are categorized by `log_type`.

### 1) Windows Security Events

- `windows_security_event` — primary Windows telemetry for all identities (users + service accounts)

### 2) Defense / Observability Logs

Defense logs represent tool outputs (alerts, blocks, denials, correlations). Common examples:

- **EDR / Endpoint:** `defender_atp_alert`, `defender_atp_detection`, `amsi_detection`, `memory_protection_block`, `credential_guard_block`
- **Identity / Privilege:** `pam_access_denied`, `credential_access_alert`, `access_control_event`, `kerberos_attack_detected`
- **Network:** `proxy_block`, `firewall_block`, `dns_query_alert`, `smb_traffic_alert`, `lateral_movement_alert`
- **Data protection:** `dlp_alert`, `dlp_block`
- **Correlation / analytics:** `siem_alert`, `behavioral_detection_alert`, `suspicious_command_line_detected`

Additional observability types may appear as the simulated defensive stack expands.

## Core Fields (All Logs)

These fields are either always present or commonly present across all log families.

| Field | Type | Required | Description |
|---|---|---|---|
| `timestamp` | string | yes | ISO 8601 timestamp with timezone, e.g. `2025-12-29T23:12:04.000-08:00` |
| `log_type` | string | yes | Log family (see [Log Type Categories](#log-type-categories)) |
| `event_type` | string | yes | High-level event type (see [Event Types](#event-types)) |
| `account` | string | yes | Security principal performing the action: user (`daniel.davis004`) or service account (`svc_*`) |
| `user` | string/null | conditional | Human identity context when available; may be null for some defense logs or pure service account activity |
| `service_account` | boolean | yes | `true` if `account` is a service account (`svc_*`), else `false` |
| `hostname` | string | yes | Device name: `WS-SAL-0005`, `WS-IT-0063`, `DB-SRV-02`, etc. |
| `device_type` | string | yes | `workstation`, `database_server`, `domain_controller`, `web_server`, `app_server` |
| `location` | string | yes | `NYC_HQ`, `SF_Office`, `London`, `Remote_VPN` |
| `department` | string | conditional | Department label for user identities (e.g. `Sales`, `IT`, `Finance`) |
| `process_name` | string | conditional | Executable/process name: `powershell.exe`, `cmd.exe`, etc. |
| `parent_process` | string | conditional | Parent process name: `explorer.exe`, `cmd.exe`, etc. |
| `command_line` | string | conditional | Full command line with arguments |
| `source_ip` | string | conditional | Source IP (internal or VPN range), e.g. `10.3.116.100` |
| `destination_ip` | string | conditional | Destination IP (internal or external), e.g. `10.x.x.x` or `203.0.113.x` |
| `port` | integer | conditional | Network port: `88`, `443`, `3389`, `8443`, etc. |
| `protocol` | string | conditional | `TCP`, `UDP`, `HTTPS`, `RDP`, `Kerberos`, `SMB`, `WinRM` |
| `session_id` | string | conditional | Session / activity grouping identifier |
| `success` | boolean | conditional | Success indicator (primarily for Windows events; may appear on some defense logs) |
| `error` | string | conditional | Error string if `success=false` |
| `event_id` | integer | conditional | Windows Event ID when applicable (e.g. `4688`, `4625`, `5156`, `4769`) |

### Key insight: `user` vs. `account`

The `account` field answers: **whose credentials performed the action.**

| Example | Meaning |
|---|---|
| `user=daniel.davis004`, `account=daniel.davis004` | Direct user activity |
| `account=svc_backup` | Service account automation (or credential misuse if labeled with `attack_id`) |
| `user` absent, `account` present | Some defense logs omit `user` but still carry `account` as the primary identity |

## Defense / Observability Fields (Defense Logs Only)

These fields appear on defense logs (when `log_type != windows_security_event`). Some may also appear on Windows events that include file hashing or extended context.

### Detection core

| Field | Type | Required | Description |
|---|---|---|---|
| `severity` | string | yes | `low`, `medium`, `high`, `critical` |
| `action_taken` | string | yes | `logged`, `alerted`, `blocked`, `denied`, `quarantined`, `isolated` (varies by log_type) |
| `alert_name` | string | yes | Human-readable alert/detection name |
| `alert_type` | string | conditional | `threat`, `behavioral`, `policy`, `rule` |
| `reason` | string | conditional | Explanation / rationale for the alert, deny, or block |
| `confidence_level` | float | conditional | `0.0`–`1.0` confidence score (tool/model confidence) |
| `vendor` | string | conditional | Defense product / control vendor name |

### Access / authentication context

| Field | Type | Required | Description |
|---|---|---|---|
| `authentication_type` | string | conditional | `Kerberos`, `NTLM`, `OAuth`, `Certificate`, `Service Account Authentication` |
| `policy_violated` | string | conditional | Policy name violated (common on DLP/PAM/access-control events) |
| `target` | string | conditional | Targeted asset/resource: `lsass.exe`, `Credential Store`, etc. |
| `target_account` | string | conditional | Account that was targeted / requested / attempted (common on PAM/access-control events) |

### Network / specialized context

| Field | Type | Required | Description |
|---|---|---|---|
| `http_status` | string | conditional | HTTP status for proxy/network events (e.g. `403 Forbidden`) |
| `query_type` | string | conditional | DNS query type: `A`, `AAAA`, `MX`, etc. |

> **Note:** Defense logs may include `command_line`, `process_name`, `hostname`, `source_ip`, and `destination_ip` when the tool attaches the triggering context. Some defense logs also include `technique` — see [Attack Labels](#attack-labels-ground-truth).

## File Hash & Reputation Fields

Hashing fields appear only on events where the simulated stack hashes an artifact — commonly `process_start`, file creation/modification events, and select network/file events.

| Field | Type | Required | Description |
|---|---|---|---|
| `sha256` | string | conditional | 64-character SHA-256 hash |
| `md5` | string | conditional | 32-character MD5 hash |
| `file_size` | integer | conditional | File size in bytes |
| `file_path` | string | conditional | Full file path, e.g. `C:\\temp\\archive.zip` |
| `signed` | boolean | conditional | Whether the artifact is digitally signed |
| `prevalence_score` | float | conditional | Approximate prevalence within the enterprise (`0.0`–`1.0`) |

**Intended semantics:**
- Known Windows binaries reuse stable hashes across events within a run
- Attacker-created scripts/archives often have rare hashes and low prevalence scores
- `signed=true` is more common for typical enterprise binaries than for attacker artifacts

## Attack Labels (Ground Truth)

Ground truth is expressed via the `attack_id` field.

| Field | Type | Required | Description |
|---|---|---|---|
| `attack_id` | string/null | yes | `ATK_50673` or `null` |
| `attack_type` | string/null | conditional | MITRE technique ID (e.g. `t1059.001`) when populated |
| `technique` | string/null | conditional | Optional alias for technique labeling (may mirror `attack_type` on some defense logs) |
| `stage_number` | string/null | yes | `"0"`–`"15"` for staged attacker actions, else `null` |

- **Benign events:** `attack_id`, `attack_type`, and `stage_number` are `null`
- **Attacker actions:** `attack_id` is non-null, with stage/technique metadata populated where applicable
- **Attack-linked defense logs:** some observability events include `attack_id`/`stage_number` to indicate linkage to attacker actions

### Kill chain mapping (ATK_50673)

| Stages | Technique | Description |
|---|---|---|
| 0–3 | `t1059.001` | PowerShell execution / initial foothold & probing |
| 4–6 | `t1087.002` | Discovery (domain / account discovery) |
| 7–10 | `t1021.001` | Remote Services / lateral movement (RDP/WinRM patterns) |
| 11–15 | `t1041` | Exfiltration over C2 channel |

### Identity progression (multi-user pivot)

| Identity | Role | Notes |
|---|---|---|
| `daniel.davis004` | Sales user | Initial compromise |
| `sarah.wilson062` | IT user (normal account) | Includes both benign admin work and attack-linked events |
| `sarah.wilson062_admin` | IT admin account | Attacker actions blend with legitimate admin patterns |

> **Important:** an attacker can continue using earlier credentials while also operating under a newly obtained privileged account. This is reflected by `attack_id != null` events appearing under multiple accounts during later stages.

## Key Notes

**String / null formatting**
- Booleans are native JSON booleans (`true` / `false`)
- Stage numbers are stored as strings (`"0"`, `"1"`, …)
- Null values are JSON `null`; missing optional fields may be absent or `null`

**Defense log behavior**
- Defense/observability logs are generated as reactions to activity (benign or attacker)
- Multiple observability events may trigger on a single attacker action
- Some defense logs include `attack_id`/`stage_number` when linked; many benign-triggered observability events have `attack_id=null`

**Network patterns**
- Internal enterprise addressing: `10.x.x.x`
- Remote/VPN addressing: `192.168.x.x`
- External endpoints use documentation ranges (e.g. `203.0.113.x`) for realism without real infrastructure

**Service account realism**
- Service accounts (`svc_*`) generate continuous high-volume activity
- Malicious use of service accounts is represented by pairing unusual context with `attack_id` labeling where applicable

## Detection Challenges (Why This Schema Matters)

This dataset is designed to surface real detection failure modes:

**Tool overlap.** The attacker uses the same tooling that admins and IT staff use — signatures alone fail.

**Privilege transitions.** The pivot into IT and IT-admin context is where naive detectors break down.

**SOC noise.** Observability logs are high-volume and overlapping, exactly what defenders deal with in practice.

**Multi-week timeline.** Actions occur over weeks, invalidating spike-based anomaly assumptions.

**Event-level ground truth.** Supports precise benchmarking and recall-by-stage analysis.
